## 0. 开工条件与文档地位

### 0.1 必须先对齐代码基线

当前本地 `main@08e3799` 不是仓库最新集成状态。`origin/main@e6df957` 已经包含：

- 五模块任务化首页；
- Zod 内容 schema、server-only repository 和页面 view model；
- 项目筛选渐进披露与 URL 状态；
- 资源健康状态、本地 SVG 产物示意；
- Vitest、Playwright、axe smoke 和 GitHub Actions；
- Phase 1.5 发布/回滚清单；
- `docs/HseeHub-phase-1.5-experience-spec.md`。

因此 Phase 1.6 的第一个 Gate 是：由仓库维护者选择合并、变基或明确舍弃 `origin/main` 的两个提交。在此之前不得按本 Spec 开始页面实现，否则会重复建设并产生大面积冲突。

本 Spec 不授权自动合并分支，也不替维护者选择基线。

### 0.2 与已有 Spec 的关系

本文件建立在 `origin/main` 的 Phase 1.5 实现之上，不重新规划已经完成的任务化首页、schema、测试和 CI。

发生冲突时：

- Phase 1.6 在首页精选数量、视觉层级、来源可信度、人工验收和发布收口范围内优先；
- Phase 1.5 的内容安全、公开只读、关系导航和工程边界继续有效；
- `HseeHub-website-architecture-spec.md` 的专业事实、安全与后续平台边界继续有效。

## 1. 决策摘要

Phase 1.5 已把 HseeHub 从“长篇内容总览”改造成“五模块任务入口”，工程质量也明显提高。下一阶段不能再做一遍首页重构；真正未关闭的问题有三类：

1. **是否真的更好用仍没有用户证据。** 发布清单中的学生、教师、读屏、200% 缩放、正式域名、预览和回滚仍为空白。
2. **页面仍有“所有内容都装进卡片”的倾向。** 首页继续展示 8 个能力入口、3 个项目卡、6 个场景入口，并大量使用边框、圆角、背景和阴影；结构缩短了，视觉层级仍偏平均。
3. **来源状态还不能表达“事实可信”与“链接可用”的区别。** 当前 `resourceHealth` 解决的是资源入口状态，不等于课程、学分或专业侧重已经被事实级复核。

Phase 1.6 的主线是：

```text
验证用户是否看懂 → 对失败点做页面减法 → 让证据与状态准确可见 → 完成可发布闭环
```

阶段完成后，团队应能回答：

- 目标学生是否能快速选对入口；
- 两个专业是否被正确理解，而不是被误解为“软件/硬件”二分；
- 用户能否从结论回到具体来源；
- 页面是否在桌面、移动、键盘、读屏和 200% 缩放下都清楚；
- 是否已经有真实预览、生产域名与可演练回滚。

## 2. 第一性原理

### 2.1 用户购买的不是内容量，而是不确定性的下降

HseeHub 的价值不是展示“我们有 8 类能力和 6 类场景”，而是帮助学生减少三种不确定性：

1. 两个专业究竟有什么共同点和不同侧重；
2. 一项能力和自己学的课程、能做的任务有什么关系；
3. 现在可以用什么小项目验证兴趣。

首页每增加一个模块、字段或卡片，都必须证明它降低了上述至少一种不确定性。否则应进入目录、详情或来源页。

### 2.2 页面存在的理由是促成下一步

每个页面遵循：

```text
一个主问题 → 一个足够继续的答案 → 必要证据 → 一个主要行动
```

首页只给“足够继续”的答案，不承担完整课程、完整能力、完整场景和完整风险说明。

### 2.3 可信度不是统一的绿色状态

必须区分：

- **事实是否经过负责人的内容复核**；
- **外部链接当前是否可访问**；
- **来源是否公开可查看**；
- **事实是否仍在复核有效期内**。

一个链接可打开，不代表某条学分或课程结论得到支撑；一份校内文件不能公开下载，也不代表其事实未经复核。

### 3.2 尚未完成或仍存在的缺口

#### P0：基线分叉

本地分支未包含上述实现。所有后续测量、截图和改动必须在对齐后的基线上进行。

#### P0：人工体验没有证据

Phase 1.5 Spec 要求 5–8 名学生、至少 1 名内容负责人、读屏、200% 缩放和外链人工复核，但仓库只有空白清单，没有结果记录。

#### P0：正式发布条件没有闭合

- 正式 HTTPS 域名未登记；
- 发布与回滚负责人未填写；
- CI 没有真实预览部署步骤；
- 没有归档 Lighthouse 和视觉回归报告；
- 回滚没有实际演练记录。

#### P1：首页仍有卡片同质化

Phase 1.5 首页使用：

- 3 张任务卡；
- 2 张专业卡；
- 1 张协作预览；
- 8 张能力快捷卡；
- 3 张项目卡；
- 6 张场景快捷卡；
- 1 个 FAQ disclosure。

页面不再是旧版长文，但大多数内容仍通过“边框 + 圆角 + 表面 + 箭头”表达。用户需要读标题才能区分“选择、比较、目录、行动和来源”。

#### P1：首页精选仍由数组顺序隐式决定

`getHomePageModel()` 使用第一条双解、`majors[0]` 的基础内容和任务数组第一个元素作为主入口。顺序变化会静默改变首页叙事。

#### P1：最后一个区段同时承担过多任务

“场景与继续探索”同时放置 6 个场景、FAQ disclosure 和来源入口。FAQ 展开后只提示用户去 FAQ 页，并没有真正回答问题，属于不必要的交互。

#### P1：事实复核仍停留在实体级

课程、学分、专业侧重通常只有一个 `sourceId` 和 `lastVerified`。没有 claim、页码/章节 locator、负责人和复核到期状态，无法证明具体结论如何对应来源。

#### P1：自动化门禁仍不完整

- Playwright 已覆盖功能与 axe，但没有视觉 screenshot 基线；
- CI 没有 Lighthouse；
- 200% 缩放和读屏仍是人工待办；
- CI quality job 构建并测试，但未提供可分享预览地址。

### 3.3 参考站可迁移的设计精髓

2026-08-17 的公开页面观察：

- 1280 × 720 下，68px sticky header 后从 y=122px 开始出现三个 66px 高的快捷入口；
- 首页正文采用约 14px 紧凑信息语法，区段标题约 16px；
- 桌面工作区为主列 + 侧栏，主列用列表、状态和元数据控制密度；
- 390 × 844 下主体宽度约 343px，快捷入口改为单列，桌面导航隐藏，侧栏排到正文之后；
- 只有真正需要浮起的入口使用明显阴影，大部分动态内容依靠分隔、类型标记和稳定对齐。

HseeHub 借鉴的是：

- 任务先于宣传；
- 一致对齐控制高密度；
- 列表、比较、状态和行动使用不同视觉语法；
- 移动端改变编排而不只是缩小；
- 工作区宽度与长文阅读宽度分离。

不复制参考站品牌、数据、社区模块、图标、颜色或像素布局。

### 4.1 目标

| ID | 目标 | 成功信号 |

## 5. 用户、任务与评分

### 5.1 参与者

- 5–8 名未熟悉两专业详细内容的高中生、新生或低年级学生；
- 至少 1 名能复核两份 2025 级培养方案的内容负责人；
- 至少 1 次 NVDA 或 VoiceOver 人工走查。

若 WP0 开始前没有招募渠道和内容负责人，WP0 不得宣称完成。开发者自测不能替代上述角色。

### 5.2 任务

#### T1 选专业入口

> 请找出两个专业共同学习什么、各自更强调什么，以及它们怎样在同一个项目里协作。

通过条件：

- 20 秒内从首页选择“专业对比”；
- 5 分钟内说出至少 3 项共同底座、各 2 项侧重和 1 个协作接口；
- 不把两个专业表述为互斥的“只做软件”和“只做硬件”。

#### T2 理解能力

> 请选择一项你感兴趣的能力，找出两个专业分别有哪些课程证据，以及这项能力能用来完成什么任务。

通过条件：

- 从首页到能力详情最多 2 次页面导航；
- 能找到两个专业的课程证据；
- 能复述一个工程任务和一个相关项目或场景。

#### T3 选择项目

> 你有大约 1–2 小时。请选择一个想尝试的项目，并说明需要什么、会得到什么、有哪些边界。

通过条件：

- 2 分钟内选择一个项目；
- 正确复述时长、基础、产物和一项安全边界；
- 不需要先展开高级筛选。

#### T4 核验事实

> 请从一个具体的课程、学分或专业侧重结论找到它的来源和复核信息。

通过条件：

- 最多 2 次操作到达证据；
- 能识别来源名称、版本/年级、定位信息、复核日期和状态。

### 5.3 计分规则

- 计时从主持人读完任务且页面可交互时开始。
- “操作”指导航、展开、筛选或点击；滚动不计操作次数，但记录滚动距离和回退。
- T1–T4 分别计分；每项任务在 5 名参与者时至少 4 名通过，6–8 名时通过人数向上取整后不得低于 80%。不能用“全部任务单元总通过率”掩盖某一项任务失败。
- 若 2 名或以上参与者在走查后仍形成“软件/硬件互斥”误解，P0 失败。
- 主持人不得提示入口；所有提示必须记录并计为未独立完成。
- 报告保存首点、耗时、回退、停顿、错误表述与最终答案，不收集健康信息或身份敏感信息。

## 6. 信息架构决策

### 6.1 一级导航

目标文案：

```text
专业对比｜能力地图｜项目入门｜应用场景
```

### 6.2 专业入口收敛

Phase 1.6 采用一个任务一个主页面：

- `/majors` 作为双专业比较的 canonical 页面；
- `/majors/compare` 使用 308 重定向到 `/majors`；
- 308 只负责路径与 query；fragment 不会发送给服务端，新 `/majors` 必须保留全部旧锚点 ID，或提供等价 alias anchor，让浏览器在重定向后自行命中；
- sitemap 不再收录旧主 URL；
- 旧 URL 的 query 必须保留；旧 fragment 必须原值可命中，不能依赖服务端做条件映射；
- 单专业详情与培养方案 URL 不变。

WP0 记录外链与发布约束；若发现阻止该方向的硬性证据，必须先修订本 Spec 并冻结唯一 `majorCanonicalRoute`，不能在实现中临时反向。redirect、metadata、sitemap、首页链接与测试矩阵都读取这一冻结决定。

### 6.3 项目筛选兼容

Phase 1.5 已支持 `major`、`capability`、`scenario`、`viewpoint`、`duration` 查询参数。Phase 1.6 视觉简化不得破坏旧分享链接：

- 合法旧参数继续生效；
- 未知值显示可恢复提示，不静默丢失；
- 清空筛选回到 `/projects`；
- 浏览器前进/后退恢复 UI；
- 参数顺序规范化但语义不变。

## 7. 首页内容与排版

### 7.1 总体约束

首页建议保持五段，但 WP0 用户证据可以合并或删除“继续探索”区段；实施目标为 4–5 个主区段：

1. 任务启动区；
2. 30 秒专业对比；
3. 最多 3 项能力捷径；
4. 3 个项目预览；
5. 继续探索与核验。

首页不得再从数组全量遍历能力与场景。3 个任务入口和现有 3 个项目是 P0 任务的固定集合；能力与场景数量是上限，不是为了版式而维持的配额。

### 7.3 任务启动区

建议文案预算：

- Eyebrow：`深圳技术大学 · 健康与环境工程学院`
- H1：不超过 18 个汉字，建议 `看懂两个专业，找到下一步`
- 摘要：不超过 50 个汉字；不重复按钮含义。
- 每个任务结果说明不超过 24 个汉字。
- 信任线只写 `专业与课程信息基于 2025 级培养方案 · 查看来源`，不把项目与场景一并包装为培养方案事实，也不显示含义不明的“全站最后核验日期”。

三个入口显式配置 `primaryJourneyId`。组件不得通过数组第一项猜测主 CTA。

只有任务入口可以使用明显阴影。移除纯装饰径向渐变，或将其弱化到不会制造假视觉焦点。

### 7.4 30 秒专业对比

首页只保留三层信息：

1. 一行共同底座；
2. 每个专业各 2 项重点任务 + 1 组代表课程证据；
3. 一个协作接口与共同产物。

完整课程、产物列表、输入、输出、验证和风险进入 `/majors`。

两个专业使用同一维度和相同顺序。不得把一边写成技术清单、另一边写成宣传段落。

### 7.5 能力捷径（最多三项）

首页精选 2–3 项能力，上限 3 项；默认选择规则是覆盖三种不同工程视角并有代表项目：

- 信号、图像与数据 AI；
- 感知、测量与医学检测；
- 设计验证与工程责任。

### 7.6 三个项目预览

## 9. 内容与证据契约

### 9.1 首页编辑配置

新增或扩展显式配置，不由数组顺序推断：

```ts
type HomeEditorial = {
  primaryJourneyId: 'compare' | 'capability' | 'project'
  featuredDualLensCaseId: string
  featuredCapabilityIds: string[] // Zod: min(2).max(3)
  projectIds: [string, string, string]
  scenarioIds: string[] // Zod: max(6)
  showExploreSection: boolean
  evidenceRecordId?: string // 数量偏离默认建议时必填
}
```

规则：

- 任务入口固定 3 个、项目固定现有 3 个；能力与场景只校验上下限；
- ID 必须存在、无重复、顺序稳定；
- 4–5 个首页主区段必须由配置显式决定，不得因空数组静默消失；
- 能力少于 3 项、场景少于 6 项或合并探索区段时，必须引用 WP0 的测试记录；
- 可选的实体关系允许显示“当前尚无已核验内容”。

### 9.2 事实复核与链接可用性分离

```ts
type ClaimSubjectType = 'major' | 'major_comparison' | 'dual_lens_case' | 'project'
type ClaimField =
  | 'totalCredits'
  | 'sharedFoundation'
  | 'focusTask'
  | 'representativeCourseGroup'
  | 'sharedGoal'
  | 'sharedArtifact'
  | 'dataBoundary'
  | 'safetyBoundary'
type ClaimKey = `${ClaimSubjectType}:${string}:${ClaimField}`

type ClaimRegistryEntry = {
  key: ClaimKey
  subjectType: ClaimSubjectType
  subjectId: string
  field: ClaimField
  normalizedContentHash: `sha256:${string}`
  evidenceRefIds: [string, ...string[]]
}

type EvidenceRef = {
  id: string
  sourceId: string
  locator?: string
  reviewedAt: string
  reviewDueAt: string
  owner: string
  reviewDecision: 'verified' | 'disputed'
}

type SourceRecord =
  | {
      id: string
      title: string
      version: string
      accessType: 'public_url'
      url: string
    }
  | {
      id: string
      title: string
      version: string
      accessType: 'institutional' | 'internal'
      accessScope: string
      url?: never
    }

type ResourceEndpoint = {
  id: string
  ownerType: 'source' | 'project'
  ownerId: string
  role: 'source' | 'tool' | 'replacement'
  required: boolean
  url: string
}

type LinkAvailability = {
  endpointId: string
  checkedAt: string
  status: 'available' | 'degraded' | 'unavailable' | 'unverified'
  replacementEndpointId?: string
  note?: string
}
```

含义：

- `ClaimRegistryEntry` 把有限字段、实体和渲染文案哈希绑定；拼错字段、实体不存在、缺证据或文案变化后仍沿用旧核验，构建必须失败；
- `EvidenceRef` 只保存复核决定，不存储可随时间变化的 `review_due`；构建用固定时钟派生 `effectiveStatus: verified | review_due | disputed | unverified`；
- `SourceRecord.accessType` 表达来源是否公开。内部正式文件显示“校内正式文件 · 无公开入口”，不创建虚假 URL，也不创建 `LinkAvailability`；
- `LinkAvailability` 只表示一个公开 endpoint 当前是否可访问，不证明内容正确；项目 `sourceUrl`、每个工具 URL 和批准的替代 URL 都先注册为独立 endpoint；
- 到达 `reviewDueAt` 后不得继续显示“已核验”。每天定时执行证据日期检查并重建线上静态站，保证最迟 24 小时内切换状态；到期前 7 天创建提醒；
- 日期派生使用构建日期，单元测试固定时钟。P0 文案哈希不匹配或证据缺失时阻止发布，非 P0 显示“待核验”。

### 9.3 Phase 1.6 必须覆盖的 claim

不要求一次性为全站所有句子建 claim。P0 事实 claim 覆盖：

- 两个专业的总学分；
- 首页与 `/majors` 展示的共同底座；
- 每个专业 2 项重点任务；
- 每个专业首页代表课程组；
- 首页精选同题双解的共同目标与产物；
- 每个项目的数据边界与安全边界。

每条 P0 claim 必须在 registry 中拥有唯一实体/字段绑定、当前内容哈希和至少一个 EvidenceRef；证据包含 `sourceId`、可用时的页码/章节/段落 locator、复核负责人、日期与决定。构建测试逐项枚举本节集合，不能只验证“存在某个 claim”。

链接 Gate 另行覆盖所有首页项目的来源入口与工具 endpoint；它只验收 `LinkAvailability` 和降级文案，不进入事实 claim 覆盖率。

### 9.4 项目资源兼容投影

Phase 1.5 的 `project.resourceHealth` 在迁移期保留为 `LinkAvailability[]` 的派生投影，避免首页与快照语义回退：

- 未有探测记录 → `unverified`；
- 任一 required endpoint 不可用且无可用替代 → `unavailable`；
- required endpoint 有批准且可用的替代，或仅 optional endpoint 异常 → `degraded`；
- 全部 required endpoint 可用 → `available`。

旧任意 `replacementUrl` 必须先注册为 `replacement` endpoint 再关联；不得把未经批准的跳转自动视作替代。迁移测试对每个现有项目比较旧、新聚合 UI 状态。

### 9.5 专业比较视图

```ts
type MajorComparisonDimension = {
  id: string
  label: string
  values: Array<{
    majorId: string
    summary: string
    evidenceRefIds: string[]
  }>
}
```

首页只读取任务与课程两个维度；完整 `/majors` 可读取更多维度。组件不得自行创作或拼接专业结论。

### 9.6 项目 quickTry

```ts
type QuickTry =
  | { enabled: false }
  | {
      enabled: true
      durationMinutes: number
      minimumArtifact: string
      startAction: { label: string; href: string }
    }
```

只有 `enabled: true` 且 `durationMinutes <= 10` 时，页面可以写“10 分钟完成”，三个字段缺一即构建失败。否则只承诺用户能在 2 分钟内比较并选择项目。

## 18. 风险与控制

| 风险 | 早期信号 | 控制 |
| --- | --- | --- |
| 在旧本地分支重复开发 | 新文件与 origin/main 大量冲突 | WP-1 阻塞全部实现 |
| 首页“精选”又变全量 | 内容负责人要求全部上首页 | schema 固定上限；全量回目录；减少数量允许引用 WP0 证据 |
| 视觉精炼变成换色 | 仍然所有模块都是卡片 | 五种任务语法验收与 screenshot review |
| 减字损害专业准确性 | 侧重被写成软件/硬件二分 | 同维度比较 + EvidenceRef + 内容负责人签字 |
| 事实状态和链接状态混淆 | “可访问”被显示为“已核验” | registry/EvidenceRef 与 LinkAvailability 两套文案、独立测试 |
| 路由收敛破坏旧深链 | `#dual-lens` 或分享链接失效 | 308/fragment/query 矩阵测试 |
| 200% 只用窄视口代替 | 自动化绿但真实 zoom 遮挡 | 真实浏览器人工 Gate |
| 视觉基线被随意更新 | 大量 diff 一键接受 | 指定维护者批准，CI 保存差异 |
| 发布前宣称真实用户 p75 | 没有 RUM 或样本 | 只用 Lighthouse 作发布 Gate；RUM 后续单独立项 |
| 继续滑向 Phase 2 | 开始讨论账号、社区或 CMS | 非目标冻结；完成本阶段后再用数据立项 |

## 20. Definition of Done

Phase 1.6 只有在以下条件全部满足时完成：

1. 本地与集成基线已对齐，Phase 1.5 已实现能力没有被重复或回退；
2. 首页完成精选和视觉语法分化，全部原有内容仍从目录可达；
3. 专业主入口已收敛，旧 URL、query 和 fragment 保持兼容；
4. 全部 P0 事实使用 claim registry 与事实级证据，文案变化会使旧核验失效，事实复核与链接可用性明确分开；
5. 学生、内容负责人、键盘、读屏和真实 200% 缩放均有实际记录；
6. 自动化、视觉回归、Lighthouse、预览、生产配置和回滚演练全部有证据；
7. 第 16.1 节所有 P0 验收通过，P1 未达项有数据、负责人和决定日期；
8. 没有以“体验优化”为由扩大到账号、社区、数据库或敏感数据处理。

完成后，团队再根据真实走查结果决定继续做内容完善、正式上线优化，还是有证据进入 Phase 2；不能按旧路线自动扩张功能。
