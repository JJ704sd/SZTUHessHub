## 0. 文档地位与启动边界

HseeHub 当前唯一有效状态是 `engineering complete / external validation blocked`。因此，本文件可以用于现在的内容盘点、线框、设计评审和后续排期，但**不改变** Release C 的状态机，也不把“下一阶段”伪写成已获准开发的 Release D。

实现本 Spec 的启动条件为二选一：

1. Release C 已依次完成 `validation candidate → validated RC → production-ready`；或
2. 产品 owner 明确批准一个仅限 preview 的例外，并同步修订 Release C 的规范和状态记录。

在启动实现前，必须把当时的工作树固定到一个可复查的提交或变更清单。当前工作树含有尚未提交的 Release C、质量门禁与视觉快照改动；本 Spec 不假定这些改动已经稳定，也不覆盖它们。

## 1. 一页决策

| 问题 | 决策 |
| --- | --- |
| 下一阶段真正要解决什么？ | 不是再加一页介绍，而是让第一次来的学生在 10 秒内选到一个低成本起点，并因看到具体结果而愿意继续探索。 |
| 首页要变成什么？ | 从按页面类型顺序铺开的说明流，变为“行动台 + 探索面板 + 轻量上下文栏”的探索桌面。 |
| 北极星闭环 | `看见一个具体问题 → 选一个入口 → 2 分钟看到相关产出/方法 → 10 分钟留下本地记录 → 继续比较或深入`。 |
| 首个主动作 | 仍是现有 `signal-feature-notebook` 的 10 分钟 Starter；它只能在首页承担一次“直接开始”语义。 |
| 不做什么？ | 不做登录、社区、评论、投稿、个人画像、排行榜、虚构学生故事、CMS、数据库、上传或第三方分析。 |
| 为什么现在只出 Spec？ | 当前代码足以验证这条路径，但 owner、许可、preview、真人测试和人工无障碍证据仍未完成；先闭环真实价值，才能判断重排是否有效。 |

一句话产品定义：**HseeHub 是让健康工程学生用一次小而真实的尝试，决定下一步该往哪里逛的探索桌面。**

## 2. 现状证据与问题定义

### 2.1 已有的强基础

- 网站已经有明确主线：“看懂专业 → 试一个小项目 → 留下真实作品 → 再看下一步”，见 [`README.md`](../README.md)。
- 首页已存在五段结构：任务启动、双专业对照、三个项目、产物/路径、核验信息，见 [`app/page.tsx`](../app/page.tsx) 与 [`components/content/home-sections.tsx`](../components/content/home-sections.tsx)。
- 站内已有足够的真实素材支撑一次探索：2 个专业、3 个项目、双专业案例、路径、FAQ、更新、合成项目预览和本地下载的 Starter；内容由 JSON 与类型化读取层提供。
- 站点已具备亮/暗主题、reduced-motion、服务端核心文本、Playwright 视觉矩阵和 axe/E2E 门禁。这些是下一阶段的硬约束，而非可以用“更好看”交换掉的质量项。

### 2.2 当前体验症状

现有首页已经不再是传统学院官网，但仍存在四个影响“继续看”的结构问题：

1. **内容节奏单一。** 首页连续使用“眉题 + 大标题 + 白色/浅色面板 + 边框”的语法；专业、项目、产物、可信信息虽不同，视觉上却像同一类说明块。桌面与移动基线可见于 [`tests/e2e/visual.spec.ts-snapshots`](../tests/e2e/visual.spec.ts-snapshots)。
2. **同一价值重复出现。** 代表 Starter 的结果预览、项目卡和产物段都在解释同一项目，用户多次遇到“曲线 + 三行观察”，却没有得到相应的新发现。
3. **主动作不是单一事实源。** `siteMeta.home.primaryJourneyId`、view model 与 [`home-sections.tsx`](../components/content/home-sections.tsx) 的固定 `starterHref`/项目 slug 存在漂移风险；一处内容配置不能可靠决定首页真正的主 CTA。
4. **信任信息出现得太早、太大。** “版本、可达、人工待复核”必须如实保留，但当前首页把它组织成一个完整尾段。它回答了审核者的问题，却不一定回答首次来访学生“我下一步能做什么”。

这不是“删掉严谨”或“换一套颜色”的问题。它是**把低承诺行动、具体回报、可信边界放到错误层级**的问题。

## 3. 从第一性原理推导

### 3.1 学生首先需要的是低成本反馈，不是完整信息

对尚未确定方向的学生，最稀缺的不是课程目录，而是一个能判断“我愿不愿意再做一次这类任务”的安全反馈回路。信息只有在它帮助做出下一步决定时才有价值。

因此首页应优先回答：

1. **我现在能碰什么？** 只给三个真实、互不重叠的入口。
2. **点进去会得到什么？** 说清时长、可见结果、最低成本与边界。
3. **如果我不想做这个，还能往哪里逛？** 给一个无需承诺的横向发现入口。

### 3.2 浏览欲来自连续的小回报

用户不会因为更长的“价值主张”继续下滑，而是因为每一屏都给出不同的问题与不同的回报：一次行动、一个对照、一段可视化结果、一个可选择的去处。首页必须让“下一屏”看起来是新的内容类型，而不是下一张说明卡。

### 3.3 信任应当即时可得，而不是占据叙事

医疗/健康教育内容不能含糊安全边界。正确做法不是在首屏堆叠合规文案，而是在每次行动附近用一句可扫读的事实说明限制；当用户需要核验时，能在一跳内抵达来源、版本、许可和状态。

`真实、可验证、不会过度承诺` 优先于 `看起来很活跃`。在没有真实供给和治理能力前，绝不以假人数、假更新、假引语或假“同学动态”制造社区感。

## 4. 对标研究：借鉴什么，不借鉴什么

参考站的可迁移精髓不是暗色背景或某一种卡片，而是以下结构：

| 参考站呈现的原则 | HseeHub 的转译 |
| --- | --- |
| 首页先给清晰动作入口，再解释价值。 | 首屏先给“试一次 / 看差异 / 先逛一条路”，不要先讲培养体系。 |
| 主内容区与轻量侧栏并置；侧栏帮助继续探索。 | 桌面端用“主探索区 + 非个人化上下文栏”；移动端把上下文栏接在行动台之后。 |
| Wiki、活动、工具等不同内容具有不同形态，但共用一致的标题、元数据和单一动作。 | Starter、专业对照、产物预览、FAQ/更新使用不同内容单元，统一使用短标题、收益/状态行和一个去向。 |
| 空状态仍给下一个选择。 | 项目、筛选或更新没有可展示项时，说明原因并给“换一个意图 / 看完整项目 / 查看来源”的可操作出口。 |
| 语气像正在使用的校园技术空间，而非公告栏。 | 使用“先试一下”“看看这两边怎么拆”“还没想好也没关系”等行动语言，但所有时间、数据、许可和资格说法仍必须可核验。 |

明确不照搬：深色 Aurora 视觉、品牌名称/图标、导航分类、账号/注册强 CTA、社区数据、排行榜、工具清单、任何原站文字或 CSS/HTML 细节。主浏览会话遇到访问验证，因此本 Spec 不以像素级复刻为目标，也不声称对外站做了逐像素验收。

## 5. 目标用户、核心任务与成功体验

### 5.1 首要用户

- 刚开始理解智能医学工程/生物医学工程差异的大一、大二学生；
- 已有一点兴趣但不知道是否值得投入的学生；
- 希望通过一个小任务而不是资格清单决定下一步的人。

教师、内容审核者和已明确求职/升学路径的人仍能使用站点，但不决定首页叙事。

### 5.2 三条首页任务

| 意图 | 用户心声 | 首页入口 | 立即回报 | 后续去向 |
| --- | --- | --- | --- | --- |
| 先动手 | “我想知道这类事我会不会想继续做。” | 10 分钟 Starter | 合成信号结果与三行观察 | 项目详情、路径或能力页 |
| 先弄懂差异 | “这两个专业到底在同一题里各干什么？” | 同题双专业对照 | 一个共同问题、两种分工、共同产物 | 专业详情、课程/能力 |
| 先逛一逛 | “我现在还没方向。” | 双路径短实验 | 两种短任务的比较方式 | 路径探索、项目目录 |

### 5.3 关键用户流

```text
首次来访
  → 10 秒内选择一个意图
  → 首次点击进入当前任务/对照
  → 看见具体结果、时长与限制
  → Starter 中完成三行观察并保存到本地
  → 选择“深入这个项目 / 看另一种分工 / 继续比较路径”
```

不要求账号、上传、打卡或返回访问。是否形成长期兴趣必须通过真人研究验证，不能由页面文案自行宣称。

## 6. 首页信息架构与版式规格

### 6.1 推荐组合：行动台 + 探索面板 + 上下文栏

桌面端（≥ 1024px）使用 `8/4` 或 `9/3` 主栏/侧栏，不在整页机械使用三栏卡片。示意如下：

```text
┌──────────────────── 全局导航：专业 / 小项目 / 能力 / 下一步 ───────────────────┐
│ 主探索区（8/9）                                      │ 上下文栏（4/3）         │
│ ┌ 今日想先搞懂哪一件事？ ──────────────────────────┐ │ ┌ 先看结果             │ │
│ │ 三个意图入口；只有一个“直接开始”                 │ │ │ 10 分钟/本地保存/边界 │ │
│ │ 主行动旁呈现真实的合成结果预览                    │ │ └──────────────────────┘ │
│ └────────────────────────────────────────────────┘ │ ┌ 小工具/常问问题       │ │
│ ┌ 继续逛：对照 / 任务 / 结果 / 更新（异构单元） ───┐ │ │ 一个轻量去向/空状态    │ │
│ └────────────────────────────────────────────────┘ │ └──────────────────────┘ │
│ ┌ 三个项目：只陈列“此刻要选哪个”，不重复直接开始 ─┐ │                           │
│ └────────────────────────────────────────────────┘ │                           │
└─────────────────────────────────────────────────────────────────────────────┘
│ 一条信任承诺：来源、版本与边界可一跳查看；页尾                                  │
└─────────────────────────────────────────────────────────────────────────────┘
```

移动端（≤ 760px）按以下次序堆叠：标题和三个入口 → 主 Starter 的结果/成本提示 → 一张对照或发现单元 → 其它项目 → 一句信任承诺 → 页尾。不得把侧栏隐藏成不可发现的抽屉，也不得让横向卡片滚动成为理解核心内容的唯一方式。

### 6.2 内容预算

首页每个区块都必须有不同的任务，避免“卡片套卡片”。

| 区块 | 首次用户的问题 | 可复用现有事实源 | 版式/动作要求 |
| --- | --- | --- | --- |
| 行动台 | 我现在可以做什么？ | `quickTry`、双专业案例、`/pathways/explore` | 3 个入口；一个主 CTA；每项给时长或承诺成本与一句收益。 |
| 结果/上下文栏 | 做了会看到什么？ | 代表项目 preview asset、Starter 边界、FAQ | 小而具体的结果预览；不展示零值个人统计；只能有一个后续动作。 |
| 探索面板 | 还有什么值得点？ | 双专业案例、项目、更新、FAQ | 2–4 个异构单元，至少包括一个对照和一个可视化/产物单元。 |
| 项目选择 | 如果不是这个，我该选哪个？ | 3 个 `featuredProjects` | 列表或分段选择器；代表项目若已在行动台“直接开始”，此处仅链接其详情，不再重复同一开始 CTA。 |
| 信任行 | 这件事能信到什么程度？ | 来源、版本、resource/claim 状态 | 首页只给一句真话和来源入口；许可、owner、完整状态进入详情和来源页。 |

首页总量上限：一个主 Starter 预览、三个意图入口、最多四个探索单元、三个项目、一个信任行。任何新增内容必须替换预算内的项目，而不是继续拉长首页。

### 6.3 区块行为

- 点击整张可交互单元时，使用语义链接；不能让纯装饰卡片假装可点。
- 每张单元只回答：**是什么、为什么现在值得点、进去会得到什么**。超过三行的解释应下沉到详情页。
- `Starter` 仅当当前状态允许时显示为“开始”；若 owner/许可/人工走通尚未批准，显示准确的体验状态和一个安全的替代入口，不用“可直接开始”掩盖待核验事实。
- 无可用更新/项目时，模块显示一条解释和一个具体出口，例如“这组内容正在复核，先看完整项目”或“换一个探索意图”。
- 同一首页模块不能同时承担“开始、解释、证据总览”三种主语义；需要多种语义时拆成不同视觉形态。

## 7. 内容模型与技术契约

下一阶段不应继续把首页选择写死在组件中。应以现有 `content/site-data.json → schema → repository/view model → Server 页面` 链路为基础，新增最小的首页编排合同。

建议的逻辑模型如下（字段名可在实现评审时调整，语义不可省略）：

```ts
homeComposition: {
  primaryJourneyId: string,
  sectionOrder: ["launch", "discover", "projects", "trust"],
  journeys: Array<{
    id: string,
    intent: "try" | "compare" | "explore",
    label: string,
    benefit: string,
    href: string,
    durationLabel?: string,
    artifact?: string,
    availabilityLabel: string,
    safetyCue?: string,
    fallbackJourneyId?: string
  }>,
  discoveryItemIds: string[]
}
```

实现约束：

1. `primaryJourneyId` 必须引用一个真实 `journey`；其链接、时长、状态和 fallback 均由同一内容对象导出。
2. 组件不得再硬编码 `signal-feature-notebook` slug、`starter` URL 或“哪个入口是主 CTA”。当前事实不变时，首页仍可选择现有 Starter；选择必须由 model 给出。
3. 每个首页入口都要通过现有内部路由/HTTPS 链接校验；无法开始的项不能伪装成已可开始。
4. discovery item 必须关联当前、具 owner/复核信息的实体。过期或未核验的内容只能进入详情页的显式状态，不进入首页的“推荐”位置。
5. 新字段要有 schema、view model、内容负向测试和首页 E2E 覆盖；不要把首页逻辑迁到客户端状态、localStorage 或新的 API。

预计触及的实现 seam 仅限：

| 区域 | 职责 |
| --- | --- |
| `content/site-data.json`、`content/updates.json` | 提供已批准的 journey、探索项目与简短状态。 |
| `lib/content/schema.ts` | 验证唯一主动作、引用完整性、状态/回退和内容预算。 |
| `lib/content/view-models.ts` | 投影为不含业务判断重复的首页 model。 |
| `app/page.tsx`、`components/content/home-sections.*` | 只编排 Server 页面和可访问的展示单元。 |
| `tests/e2e/home.spec.ts`、`tests/e2e/visual.spec.ts` | 保护主路径、非重复 CTA、移动重排及亮/暗主题基线。 |

不新增数据库、账号、实时 API、分析 SDK、图片 CDN 或生产依赖。当前 `lib/analytics.ts` 没有 production sink；若将来需要聚合行为数据，必须另立隐私 Spec，先定义同意机制、数据最小化、保留期、owner、DNT/Cookie 行为和删除策略。

## 8. 视觉、交互与文案系统

### 8.1 目标气质

目标不是“更像学校官网”，而是**一张有人正在用的工程探索桌**：安静、有内容密度、能一眼看到可做的事，也能一眼看出它的边界。

- 保留现有蓝/青语义色、亮/暗主题 token、紧凑导航和无障碍焦点样式；不要复制参考站配色或背景效果。
- 让合成预览、流程图、对照和短清单承担视觉变化，减少每段都用大标题和大圆角白卡。
- 只保留三类表面：行动单元（显著）、探索单元（轻表面）、可信/状态行（非卡片或弱分隔）。当一个元素不需要独立点击或状态，就不加阴影和边框。
- 图片/图表只使用现有原创 SVG 或有来源、许可、alt 和核验日期的新资产；不使用真实患者数据，不生成伪纪实学生照片。
- 不以动效吸引注意；hover、展开和筛选必须在键盘、触摸和 `prefers-reduced-motion` 下等价可用。

### 8.2 文案规则

首页文案用动作和结果开头，避免把内部治理语言暴露成用户的第一阅读成本。

| 需要表达的事 | 推荐写法 | 不推荐写法 |
| --- | --- | --- |
| 主标题 | “今天想先搞懂哪一件事？” | “健康工程综合探索平台” |
| 行动入口 | “试一次 10 分钟 Starter” | “进入项目实践模块” |
| 专业对照 | “同一道题，两边怎么拆？” | “专业培养差异分析” |
| 状态边界 | “合成数据 · 本地保存 · 资源核验中” | 把“人工与许可待复核”藏起来，或写成大段审核说明 |
| 来源入口 | “这页从哪来，也把边界说清” | “依据与最近核验” |

所有轻松语气都要通过事实校验：不暗示学生已经参与、项目已经获得许可、资源已经保证可用，或某个学习结果能够证明临床/职业能力。

### 8.3 响应式与可访问性

- 保持现有 1440、768、390px 视觉矩阵，并加测 320px reflow、200% zoom、暗色、forced-colors、键盘、打印和读屏。
- 主 CTA、焦点、状态与交互不能仅靠颜色区分；状态文本必须在亮暗主题都可读。
- 所有图形有正确 alt 或明确的装饰标记；图表不能是理解关键结论的唯一途径。
- 390px 首页仍须满足 Release C 的 `≤ 4400px` 约束；信息量增加时先做替换和下沉，而非延长页面。

## 9. 验收标准与研究设计

视觉快照只能证明回归稳定，不证明用户想继续看。下一阶段应沿用 Release C 的两轮 5 人目标学生测试，增加以下体验观察；真人记录仍写入现有 [`student-test-record.md`](release-c-validation/student-test-record.md) 或其获准的后续版本。

### 9.1 体验通过线

| 检验 | 通过标准 |
| --- | --- |
| 五秒理解 | 5 名中至少 4 名可说出“这里能让我试一次、看差异或找下一步”，而不是把它称为学院介绍页。 |
| 十秒定向 | 5 名中至少 4 名无需提示即可指出自己会点的一个入口，并能说出点击后会得到什么。 |
| Starter 可完成 | 5 名中至少 4 名在 12 分钟内完成三行观察、下载/定位本地文件，并说出一项不可外推的限制。 |
| 浏览奖励 | 5 名中至少 4 名在主入口以外，自发点开一个不同内容类型的单元；主持人记录其原因和原话。 |
| 非重复理解 | 5 名中至少 4 名不会把同一 Starter 的预览、项目条目和产物说明误认为三项不同活动。 |
| 移动扫描 | 至少 3 名主要使用手机的参与者能在前两屏找到可做的 Starter，不因侧栏/卡片横滑迷路。 |

### 9.2 工程与内容通过线

- 首页仅有一个直接指向 Starter 的主 CTA；同项目的其它出现不重复“开始”语义。
- `primaryJourneyId` 与真正渲染的 CTA、href、状态一致，并由 schema/test 反向覆盖。
- 首页所有“推荐”实体有当前来源、owner、更新时间和复核日期；不具备这些事实的内容不成为推荐卡。
- 保留所有 Release C 安全边界、服务端文本、性能预算、视觉矩阵、a11y 与链接/内容校验。
- 在获准的 preview 中完成两轮目标用户测试、人工无障碍走查和两次清洁环境门禁；不得用本地截图、自动化或生成数据替代。

## 10. 分阶段交付与依赖

| 阶段 | 交付物 | 完成条件 | 不可跳过的依赖 |
| --- | --- | --- | --- |
| A. Release C 闭环 | owner/许可、preview、两轮测试、人工 a11y、回滚与双次门禁证据 | 状态机达到 `production-ready`，或有正式 preview 例外 | [`exit-plan.md`](release-c-validation/exit-plan.md) 的顺序和证据规则 |
| B. 体验定稿 | 内容预算表、低/高保真响应式线框、内容状态清单、迁移 PRD | 产品/内容/无障碍 owner 一致确认主路径、状态文案和替代入口 | 以实际稳定提交为基线，不拿未提交快照直接开工 |
| C. 首页与模型收敛 | `homeComposition` 合同、行动台/探索面板/上下文栏、迁移测试和新视觉基线 | 所有首屏 CTA 来自 model；移动、键盘、暗色和性能检查通过 | 不新增内容域、后端或分析 SDK |

| E. 发布判断 | 发布决定、监控/反馈安排、回滚证据 | 满足当时规范的全部发布门槛 | 不把“设计已完成”当作发布条件 |

## 11. 风险与控制

| 风险 | 为什么会发生 | 控制措施 |
| --- | --- | --- |
| 变成参考站换皮 | 把研究误读为抄深色、卡片和账号机制 | 评审以“行动入口、内容异构、探索退出”三条原则验收，不审相似度；禁止复制资产/文案。 |
| 为了活跃感虚构社区 | 当前没有可验证的用户内容供给 | 只展示已批准的项目、预览、FAQ、更新和来源；真实作品/访谈必须有许可、作者/编辑范围与撤回规则。 |
| 把核验信息藏掉 | 想让首屏更轻，会诱发过度承诺 | 每个行动附近保留简短、明确状态；完整证据一跳可达；状态不佳时走 fallback。 |
| 改动越做越大 | 视觉重排诱发账号、feed、CMS 等扩张 | 严格执行第 1 节非目标；任何新增持久化/第三方数据流单独立项。 |
| 当前工作树混入基线 | 已有未提交 Release C 改动和快照 | 开发启动时先固定基线、审阅 diff，文档/代码/快照按同一变更集验证。 |
| 只凭审美判定成功 | 视觉截图看起来更新，但学生任务仍失败 | 两轮目标学生测试和人工无障碍是硬门槛；记录原话、时间与失败步骤。 |

## 12. 开工前待确认的决策

1. 谁是 Starter、专业事实、视觉、无障碍、preview 与发布的具名 owner？
2. Release C 何时可以提供可分享、无索引的 preview，并允许招募 5+5 名目标学生？
3. 可用于探索面板的新增素材是否有真实作者、许可、用途范围、alt 和撤回路径？若没有，维持现有原创 SVG 与编辑内容。
4. 是否只在 Release C 完成后实施，还是由产品 owner 批准一个有明确范围的 preview 例外？
5. 若未来要衡量线上行为，是否愿意单独批准隐私/数据保留 Spec？在答案为“否”时，继续使用匿名现场任务记录，不接入埋点。

---

**最终判断：** HseeHub 的下一阶段不应把首页做成更华丽的专业介绍，也不该伪造成一个已经活跃的社区。它应把已有的真实 Starter、专业对照、项目预览和路径内容编排成一个有节奏的探索桌：先让学生找到一件想碰的事，再用具体结果给他继续浏览的理由，同时始终诚实地说清边界。
