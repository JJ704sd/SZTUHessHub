## 1. 决策摘要

下一阶段不增加登录、社区、数据库或更多内容域，而是把已经齐全的内容从“完整陈列”改造成“快速理解并采取下一步”的学生探索工具。

阶段名称确定为：

> **Phase 1.5：体验压缩、关系闭环与发布验证**

本阶段选择“内容内核 + 服务端查询 + 页面最小投影 + 内容无关 UI 原语”的中等重构方案。先修复内容和组件边界，再重做首页与关键任务流，最后补齐学生走查、可访问性、自动化测试和发布门禁。

本 Spec 的核心交付是：

1. 首页从 7 段连续说明页改为不超过 5 个模块的任务启动台。
2. 首屏直接提供“看懂专业、理解能力、试一个项目”3 个入口。
3. 完整证据、课程详情、安全边界和长解释保留，但从列表态移入详情页或按需展开区。
4. 专业、课程、能力、项目、场景之间的可见关系均可导航，消除“死标签”。
5. 项目发现从 5 个常驻筛选器改为结果优先、筛选按需展开。
6. 阻止完整内容 JSON 进入客户端包，建立可测试的内容模型和页面投影。
7. 完成首版尚未关闭的学生理解、键盘、200% 缩放、屏幕阅读器、外链状态、CI 和回滚门禁。

### 1.1 与旧 Spec 的关系

本文件是 `HseeHub-website-architecture-spec.md` 的增量执行规范。发生冲突时，本文件只在以下范围内优先：

- 覆盖旧 Spec §4.3 的“完整单列 GuideLanding”首页顺序；
- 覆盖旧 Spec 中让完整内容卡直接进入首页的展示约定；
- 细化旧 Spec §6 的视觉密度、渐进披露与媒体资产规则；
- 细化旧 Spec §7–§13 的内容边界、测试和发布门禁；
- 在完成本阶段验收前，暂停进入旧 Spec 的 Phase 2 动态能力。

以下既有边界继续有效：

- 4 个一级内容域不变；
- 默认内容版本仍为 2025 级；
- 内容事实仍可追溯到来源、版本和最后核验时间；
- 不排名专业，不替学生作专业选择；
- 不处理真实患者数据，不给出诊断或治疗建议；
- 不在站内运行不可信代码、模型训练或医院/校园生产系统；
- 首版保持公开只读，不发布空的后续路由。

## 2. 当前基线与问题证据

### 2.1 已有产品能力

当前仓库已实现可工作的 Next.js 内容站，而非绿地项目：

- Next.js 14.2、React 18、TypeScript、Zod 依赖；
- 2 个专业、2 个“同题双解”、8 类能力、3 个项目、6 类场景、6 个 FAQ、8 条来源；
- 首页、专业总览/对照/详情/课程版本、能力索引/详情、项目索引/详情/资源、场景索引/详情、来源和关于页面；
- 亮暗主题、响应式导航、语义 CSS token、URL 可分享的项目筛选；
- 源码、内容关系、外链协议、类型和生产构建门禁。

基线 `npm.cmd run check` 已通过，生产构建生成 38 个页面产物。首页 First Load JS 为 96.2KB，`/projects` 为 113KB。

### 2.2 首页密度基线

在 1280×720 的同一浏览器测量口径下：

| 指标 | 当前 HseeHub | 参考站公开首页 | 解释 |
| --- | ---: | ---: | --- |
| `body.innerText` 非空白字符 | 5,499 | 775 | 两站内容目的不同，只用来暴露量级差异 |
| 页面高度 | 8,251px | 1,747px | 当前首页约 11.5 个视口，参考页约 2.4 个视口 |
| 首页主要结构 | Hero + 7 个完整叙事段 | 快捷入口 + 紧凑列表/侧栏 | 当前首页承担了过多详情职责 |
| 媒体表达 | 3 个项目 CSS 抽象图形 | 以 SVG 图标、色标、日期块和分区为主 | “视觉感”不等于大量摄影图 |

当前首页一次展开约 29 个内容单元：2 个专业、2 个完整双解、8 个能力、4 个学习阶段、3 个项目、6 个场景和 4 个 FAQ。问题是结构性的，不应通过缩小字号或压紧行距来解决。

### 2.3 首屏问题

用户截图中的首屏由以下内容占据：

- 大字号长标题；
- 多行定位说明；
- 2 个按钮；
- 独立的内容边界说明卡；
- 装饰圆；
- 3 个统计数字。

第一组真正帮助比较专业的内容接近下一屏。用户要先阅读“网站是什么”，才能看到“现在可以做什么”。这与既有“任务先于宣传”原则相反。

### 2.4 渐进披露不足

- `DualLensCard` 在列表态已展示角色、输入、输出、接口、共同产物、验收和风险边界，基本等同详情页。
- 首页、`/majors`、`/majors/compare` 重复展示共同底座与同题双解。
- `/capabilities` 同时展示 8 张完整卡和一份可见文字等价列表，却没有形成真正的视觉关系入口。
- 首页和详情页普遍重复“眉题 + 大标题 + 描述 + 操作 + 重卡片”语法。

### 2.5 关系导航断点

内容数据已经存在专业、课程、能力、项目和场景的关系 ID，但部分页面只把它们显示为不可点击标签：

- 课程上的能力标签不能进入能力详情；
- 项目详情的专业、能力和场景标签不能进入对应详情；
- 能力详情没有直接列出相关项目与场景；
- 首页能力卡声称有课程证据，但实际卡面没有呈现该关系。

### 2.6 工程边界问题

`ProjectBrowser` 为复用 `Badge` 从混合组件模块导入；混合模块顶层又导入完整 `siteData`。结果是完整约 42.9KB 的内容 JSON 可进入 `/projects` 客户端依赖链，且筛选组件接收远多于列表所需的详情字段。

此外，当前存在三套可能漂移的内容事实定义：

1. 手写 TypeScript 类型；
2. 较浅的运行时解析；
3. 独立的构建校验脚本。

本阶段需要把类型、运行时解析和关系约束收敛到同一 schema 内核。

### 2.7 尚未完成的首版验收

当前门禁可以证明“能构建”，但不能证明“学生用得懂”：

- 尚无目标学生/教师语言评审记录；
- 尚无单元、组件、E2E、axe 或视觉回归测试；
- 尚未完整验收 200% 缩放和屏幕阅读器任务流；
- 外链脚本只检查 HTTPS/格式，不检查真实可用状态或替代资源；
- 尚无仓库 CI、预览发布和正式回滚证据。

## 3. 阶段目标与非目标

### 3.1 产品目标

| ID | 目标 | 成功信号 |
| --- | --- | --- |
| G1 | 新访客先看到任务，而不是长篇定位说明 | 首屏可见 3 个核心任务入口 |
| G2 | 降低首页阅读负担但不删除证据 | 首页初始可见文字减少，详情仍完整可追溯 |
| G3 | 把内容实体变成可探索关系网 | 关系标签可点击，关键任务流不超过 3 次操作 |
| G4 | 让 3 个项目易于直接比较 | 无需先操作 5 个筛选器即可选项目 |
| G5 | 用有信息含量的视觉替代重复散文 | 对照、流程、产物或状态图进入关键卡片 |
| G6 | 建立能安全迭代的工程接缝 | 完整内容不进入客户端，页面使用最小投影 |
| G7 | 关闭 Phase 1 的真实体验与发布门禁 | 学生测试、a11y、E2E、CI、外链状态和回滚有证据 |

### 3.2 非目标

本阶段明确不做：

- 登录、账号、收藏、跨设备进度；
- 社区、评论、投稿、举报、审核后台；
- 动态活动流、日历、通知或个人热力图；
- CMS、数据库、搜索服务或微服务；
- 新增大规模专业、课程、岗位或项目内容；
- 真实患者数据、文件上传、站内 Notebook、模型训练或代码沙箱；
- 复制参考站的品牌、文案、图标资产、页面数据或 7 项导航；
- 以纯装饰大图代替内容设计；
- 为压缩文字而删除来源、许可、版本、安全和医学责任信息。

## 4. 核心用户与任务

### 4.1 主要用户

1. **第一次了解专业的学生**：不知道两个专业的共同点和侧重，需要快速建立正确心智模型。
2. **想把课程连接到实际任务的在读学生**：知道课程名，但不知道能力能完成什么、还能迁移到哪里。
3. **想低成本试一个方向的学生**：希望先知道时长、先修、产出和风险，再决定是否打开外部工具。

教师与内容维护者是重要审核角色，但首页不以其维护任务为主线。

### 4.2 核心 JTBD

| 用户情境 | 用户任务 | 首页入口 | 期望结束状态 |
| --- | --- | --- | --- |
| “我在选专业” | 看懂共同底座、不同侧重与协作接口 | 看懂两个专业 | 能说出共同点、各两项侧重和一个接口 |
| “我不知道课程以后能做什么” | 从任务理解能力与课程证据 | 从能力看任务 | 能选一项能力并找到课程、项目和场景 |
| “我想先动手试试” | 比较时间、先修、产出和安全边界 | 试一个项目 | 能选择一个合适项目并复述成本与产出 |

### 4.3 核心任务流

```text
看懂专业：/ → /majors/compare → /majors/[majorSlug] 或相关项目
理解能力：/ → /capabilities → /capabilities/[capabilitySlug] → 相关项目/场景
尝试项目：/ → /projects → /projects/[projectSlug] → /resources 或官方资源
```

规则：

- 从首页到目标详情最多 3 次操作；
- 每个详情页必须给出一个语义明确的下一步；
- 下一步文案必须描述结果，例如“比较两个专业”“查看相关项目”，不使用泛化的“了解更多”；
- 返回上层不能只依赖浏览器后退。

## 5. 体验与视觉原则

### 5.1 可借鉴的参考站精髓

| 原则 | HseeHub 的实现方式 |
| --- | --- |
| 任务先于宣传 | 首页顶部直接显示 3 个学生任务入口 |
| 高密度统一语法 | 卡片使用“类型/图标 + 标题 + 一行说明 + 元数据 + 单一操作” |
| 视觉用于定位 | 使用图标、流程线、对照矩阵、时长块、状态和产物缩略图 |
| 公共信息与上下文并置 | 只在有真实价值时显示来源/版本/推荐项目上下文，不造个人数据 |
| 留白用于分组 | 重大区段 48–64px，卡片 16–24px，避免连续 86px 大留白 |
| 详情按需展开 | 首页讲人话，证据和边界进入详情或原生 disclosure |

### 5.2 不照搬的部分

- 不增加参考站的登录、Wiki、社区、活动、职业和实验室模块；
- 不复制暗色品牌、布局尺寸或 SVG 资产；
- 不采用缺失显式 H1 的页面结构；
- 不复制参考站移动顶栏拥挤、字号碎片和断点碎片；
- 不因为参考站首页短，就牺牲 HseeHub 的专业证据与医疗安全边界。

### 5.3 内容分层

每项内容分为三层：

| 层级 | 出现位置 | 回答的问题 | 预算 |
| --- | --- | --- | --- |
| L0 入口 | 首页任务卡/导航 | 我现在可以做什么？ | 标题 ≤14 个汉字；说明 ≤24 个汉字 |
| L1 摘要 | 索引卡/关系图 | 这是什么，为什么值得点？ | 摘要 ≤48 个汉字；最多 3 个关键标签 |
| L2 证据 | 详情页/按需展开 | 依据、版本、输入输出、风险和下一步是什么？ | 不设武断字数，使用阅读宽度和章节层级控制 |

约束：

- 列表卡不得直接承载详情页的完整输入、输出、接口、验收和风险段落；
- 首页 teaser 正文最多两行；
- 一张卡最多一个主操作；
- 不能通过 CSS 行数截断隐藏唯一存在的关键事实；被截断内容必须在详情中完整可达；
- 安全状态、数据级别和来源状态不是普通长文，应以短标签/状态行表达。

### 5.4 信息视觉优先级

优先使用：

1. 双专业共同底座与两种透镜的视觉矩阵；
2. “课程 → 能力 → 任务 → 项目/场景”的短关系链；
3. 项目预期产物、信号链、系统框图或选型矩阵的缩略示意；
4. 时长、先修、数据状态、来源状态和安全状态；
5. 场景的“可复用 / 需补门槛”二分结构。

纯渐变、装饰圆或无信息照片不计入“视觉化内容”验收。

### 5.5 动效

- hover/focus 位移不超过 2px；
- 普通过渡 160–220ms，颜色主题过渡不超过 300ms；
- 不使用自动轮播、视差、持续漂浮或必须等待的滚动揭示；
- 动效不作为唯一状态反馈；
- `prefers-reduced-motion` 下取消非必要位移和连续动画。

## 6. 信息架构与首页规范

### 6.1 一级导航

继续保留：

- 学院与专业；
- 能力与课程；
- 项目探索；
- 发展场景。

不新增一级入口。品牌继续返回首页，来源、FAQ 和关于放在上下文链接或页脚。

桌面可在不挤压导航的前提下加入紧凑的“5 分钟对照”行动入口；移动端仍只保留品牌、主题和具名菜单按钮。

### 6.2 首页总体约束

- 主模块最多 5 个；
- 桌面 1440×900 的页面高度目标不超过 4 个视口；
- 移动 390×844 的页面高度目标不超过 6 个视口；
- 首页初始可见非空白正文目标 ≤3,000 个字符；测量口径为 `<main>.innerText` 去除空白字符，关闭的原生 disclosure 内容不计入；该指标是密度警戒线，不能替代学生理解测试；
- 同一种完整内容不得同时出现在首页和一级详情页；
- 1440×900 与 390×844 首屏无需滚动即可看到 3 个核心任务入口；
- 首屏除全局导航外至少有 4 个有效任务链接；
- 第一个任务入口顶部距 `<main>` 起点不超过 120px；
- 首屏解释性正文不超过 140 个中文字符；
- H1 桌面 44–52px、移动 32–38px，最多两行且高度不超过视口的 15%。

### 6.3 模块 1：任务入口区

结构：

```text
短眉题
H1：一句学生能理解的价值说明
不超过两行的补充说明
[看懂两个专业] [从能力看任务] [试一个项目]
版本 · 来源 · 内容边界（单行信任信息）
```

任务卡：

| 入口 | 目的路由 | 卡片信息 |
| --- | --- | --- |
| 看懂两个专业 | `/majors/compare` | 共同底座、不同侧重、如何协作 |
| 从能力看任务 | `/capabilities` | 课程能形成什么能力、可以做什么 |
| 试一个项目 | `/projects` | 先看时长、基础和产出，再决定是否开始 |

要求：

- 桌面横排，移动单列；
- 每张卡高度 64–88px，整卡可点击；
- 每张卡有独立图标且图标含义可被文本说明；
- 保留一个主优先入口，但 3 个入口都具备清晰可达性；
- 移除独立大尺寸“内容边界说明卡”和统计条；版本与来源压缩为一行信任信息。

### 6.4 模块 2：双专业一屏对照

目标：一屏回答“共同学什么、各自更强调什么、在哪里协作”。

结构：

- 顶部：共同底座 3–5 项；
- 左右：两个专业透镜，各显示最多 3 项侧重；
- 中部或底部：1 个精选协作接口与共同产物；
- 操作：进入完整对照。

首页不再渲染：

- 完整 FoundationTable；
- 两个完整 DualLensCard；
- 学分结构长免责声明；
- 每个透镜的完整输入/输出/接口/验收/风险。

这些内容完整保留在 `/majors/compare` 和专业详情页。

### 6.5 模块 3：能力捷径

8 类能力改为紧凑图标网格。首页每项只显示：

- 图标；
- 任务语言名称；
- 一句典型任务；
- 指向能力详情的整卡链接。

首页不显示完整迁移摘要和课程证据列表。区段内增加一条简短关系说明：

```text
课程证据 → 可证明的能力 → 项目/场景
```

完整课程证据、健康样例、跨行业样例和新增门槛进入能力详情。

### 6.6 模块 4：今天先试一个

保留 3 个首发项目，但把卡面改为“结果预览”而非长摘要：

- 25%–35% 卡面用于有信息含量的项目视觉；
- 显示时长、适合基础、预期产物、数据/安全状态；
- 摘要不超过 48 个汉字；
- 每张卡只有“查看体验卡”一个主操作；
- 双专业协作项目有清晰协作标记。

视觉示例应分别对应：

- 合成信号曲线/特征表；
- 传感—采样—提示系统框图；
- 材料/检测选型矩阵。

视觉必须有文本等价信息，但不要求等价长文与图同时全部展开。

### 6.7 模块 5：场景与继续探索

6 类场景压缩为图标/标签入口。每项只显示：

- 场景名称；
- 1 个可复用能力；
- 1 个需要补充的门槛。

区段末尾提供 FAQ 与来源入口。首页最多展示一个高频问题的标题，不默认展开完整答案。

四年学习故事移出首页，进入专业总览或专业详情。

## 7. 关键页面改造

### 7.1 `/majors/compare`

- 首屏使用视觉矩阵：共同底座在上，两种专业透镜并排，协作接口/共同产物居中；
- 完整课程结构、来源和“不作排名”说明继续保留；
- 完整同题双解采用摘要 + 原生 disclosure 或独立锚点；
- 每个同题双解先显示共同问题、两种贡献和共同产物，再按需展开输入/输出/接口/验收/风险；
- 提供相关能力和相关项目的直接链接。

### 7.2 `/capabilities`

- 8 个任务型入口先行，不再同时默认展开完整卡和完整文字等价列表；
- 视觉关系图若启用，必须有可聚焦节点、文本等价入口和无 JS 可读退化；
- 首页和索引使用短投影，详情页负责课程证据与跨场景解释；
- 每个能力详情列出直接相关的课程、项目和场景。

### 7.3 `/projects`

当前只有 3 个项目，不常驻展示 5 个下拉框。

默认界面：

- 直接显示 3 个可比较项目；
- 首层只保留“时长”和“项目视角”两个高价值快捷条件，或使用 3 个任务预设；
- 专业、能力、场景等进入“更多筛选” disclosure；
- 已选条件以可删除 chip 显示；
- 无结果时一键回到全部项目；
- URL 继续保存筛选状态。

当项目数量大于 6，且用户测试证明筛选有价值时，才允许默认展开更多筛选。

渲染决策必须在 T0 关闭并记录 ADR，不能拖到发布前：

- 若正式托管已确认支持 SSR，则保留 `/projects` 为唯一允许动态 SSR 的公开页，以保证分享 URL 首屏与筛选一致；该页必须使用最小页面投影和明确缓存策略。
- 若正式托管不支持 SSR，或 T0 结束时仍无法确认，则默认采用静态方案：构建时输出全部项目，客户端渐进增强读取 URL 并应用筛选；无 JS 时全部项目可读，hydration 后 CLS 仍需 ≤0.1。
- 两条路径都必须通过筛选分享 URL、无结果恢复、最小客户端投影和 3 个项目直接比较的同一组 E2E；不得在 T1 后静默切换。

### 7.4 `/scenarios`

- 卡片统一为“可迁移 / 需补门槛”两栏；
- 用图标和约束标签替代重复长摘要；
- 每个场景详情列出直接相关的能力和项目；
- 医疗与非医疗场景继续显示不同错误成本、标准和责任边界。

### 7.5 详情页共同模板

- 主阅读列 720–800px；
- 桌面可使用 sticky 页内目录，移动端为可展开目录；
- 顶部关键事实条显示版本、时长、来源或状态；
- 段落按“结论 → 证据 → 边界 → 下一步”组织；
- 每页只设置一个主行动，次级关系使用文本链接；
- 页面末尾提供相关内容和明确的上层返回入口。

## 8. 关系导航规范

### 8.1 可导航关系

以下可见实体必须使用链接而非纯 badge：

- 专业 → 课程版本、能力、项目；
- 课程 → 专业、能力；
- 能力 → 课程、项目、场景；
- 项目 → 专业、能力、场景、资源；
- 场景 → 能力、项目。

状态、版本、数据敏感级别等非实体标签继续使用普通 badge，不能伪装成链接。

### 8.2 关系呈现规则

- 链接文字使用实体名称，不使用裸 ID；
- 关系链接有可见 hover/focus 状态；
- 整卡链接中不得再嵌套冲突的交互元素；
- 相关内容按相关性或明确规则排序，不随机；
- 每组默认展示 3–5 项，其余按需展开；
- 反向关系由内容模型派生，不在 JSON 中重复维护两份事实；
- 任意关系目标不存在时必须在构建期失败。

### 8.3 关系验收

每类实体至少抽查 2 个样本，完成正向和反向导航。不存在只有文本、看似可点但不可到达的关系标签。

## 9. 内容与媒体模型

### 9.1 单一内容内核

目标结构：

```text
lib/content/
├─ schema.ts        # Zod schema、refine、由 schema 推导 TypeScript 类型
├─ repository.ts    # `server-only`，加载本地 JSON 和操作型查询
├─ view-models.ts   # 首页、索引、客户端所需的最小投影
└─ index.ts         # 只导出服务端安全入口与类型
```

规则：

- 使用 Zod 作为运行时解析与 TypeScript 类型的单一来源；
- 把现有数量、关系、版本、安全措辞和跨字段规则迁入 schema/refine 或调用同一 schema 的校验器；
- `repository.ts` 明确 `import 'server-only'`；
- 不为了未来 CMS 预先设计通用仓库接口；当前使用 `getHomePageModel()`、`getProjectCatalog()`、`getMajorBySlug()` 等操作型查询；
- 构建脚本和应用读取必须调用同一 schema，避免三套规则漂移；
- `sources` 同样检查 ID 唯一、日期、URL、版本和许可字段。

### 9.2 页面投影

示例：

```ts
type ProjectCatalogItem = {
  id: string
  slug: string
  title: string
  cardSummary: string
  majorIds: string[]
  capabilityIds: string[]
  scenarioIds: string[]
  viewpoint: string
  durationBands: string[]
  durationLabel: string
  prerequisiteSummary: string
  outputSummary: string
  dataStatus: string
  visualAssetId?: string
}
```

客户端只能接收交互所需的投影，不能接收完整 `Project`、`Major`、`Capability`、`Scenario` 集合。

### 9.3 短文案字段

为需要进入入口/列表态的实体增加受校验字段：

- `navigationLabel`：任务型短名称；
- `cardSummary`：≤48 个汉字的列表摘要；
- `taskSummary`：典型任务短句；
- `outputSummary`：项目产出短句；
- `primaryAction`：操作文案与目标；
- `visualAssetId`：可选视觉资产关系。

不要在组件内用 `slice()` 从长文案临时截取业务文本。旧长字段继续作为详情内容。

### 9.4 媒体资产合同

```ts
type MediaAsset = {
  id: string
  src: string
  width: number
  height: number
  alt: string
  decorative: boolean
  role: 'hero' | 'card' | 'diagram' | 'evidence'
  caption?: string
  sourceId?: string
  license: string
  lastVerified: string
}
```

校验规则：

- 本地文件必须存在；
- `width`、`height` 必须为正数；
- 信息图必须有描述性 `alt` 或邻近文字等价；
- `decorative=true` 时 `alt` 必须为空；
- 非原创资产必须关联来源、许可和核验日期；
- 不允许把远程图片热链作为核心首屏依赖；
- 摄影/位图优先 AVIF/WebP，固定尺寸并提供 `sizes`；
- 纯图标和简单关系图优先本地 SVG/CSS，不增加客户端 JS。

### 9.5 外部资源状态

项目资源增加：

```ts
type ResourceStatus = 'available' | 'degraded' | 'unverified' | 'unavailable'

type ResourceHealth = {
  status: ResourceStatus
  checkedAt: string
  replacementUrl?: string
  note?: string
}
```

- 构建期只校验 schema、协议和允许规则，不依赖外网；
- `status` 表示 `checkedAt` 时的最后已知状态，不承诺运行时实时感知第三方站点变化；
- 定时或发布前任务检查真实可用性、重定向和证书，生成版本化健康快照（例如 `content/resource-health.json`）和差异报告；
- 定时 CI 对状态变化创建待审阅 PR 或等价变更，合并后触发站点重建；不引入数据库，也不让未审阅探测结果直接自动发布；
- 资源失效只降级对应卡片，不阻断全站构建；
- `unavailable` 必须显示原因和替代入口，或明确没有替代资源；
- “待人工核验”不得永久作为所有资源的固定状态。

## 10. 前端架构

### 10.1 组件边界

目标结构：

```text
components/
├─ ui/          # Badge、Button、Heading、Disclosure、Icon
├─ content/     # MajorCard、CapabilityCard、ProjectCard、ScenarioCard
├─ shell/       # Header、Footer、SkipLink、PageNav
└─ visuals/     # DualLensDiagram、RelationChain、ProjectPreview、StatusGraphic
```

规则：

- `ui/` 不导入 `siteData` 或服务端内容模块；
- 数据感知的 Footer 留在 `shell/`，只接收其所需投影；
- 删除未使用参数和无效依赖，例如未使用的 `majorMap`；
- Server Component 默认，只有筛选、主题、菜单和必要 disclosure 交互客户端化；
- 不因视觉改版把整个首页转成 Client Component；
- 复杂视觉可用服务端生成的 HTML/SVG，不默认引入图表库。

### 10.2 CSS 迁移

- 保留 `globals.css` 中的 token、reset、布局和兼容规则；
- 新增/改造组件优先使用 CSS Modules，避免一次性重写 400+ 行全局 CSS；
- 语义 token 继续作为亮暗主题唯一颜色入口；
- 移除只为旧首页结构服务且无调用的样式前，先通过引用检查；
- 禁止在组件内硬编码已存在的颜色、间距和断点语义。

### 10.3 客户端包约束

- `/projects` 客户端 chunk 不得包含 `siteMeta`、FAQ、来源、课程详情或完整 `site-data.json` 文案；
- `/projects` 路由特有 JS 目标 ≤12KB（当前约 17KB）；
- 首页 First Load JS 不高于当前 96.2KB 基线，硬上限 100KB；
- 全站任一公开页 First Load JS 不超过既有 150KB 预算；
- 添加图标或视觉不得引入整包图标库；使用可 tree-shake 的单图标导入或本地 SVG。

## 11. 可访问性与响应式

### 11.1 WCAG 目标

以 WCAG 2.2 AA 为交付线：

- 普通文字对比度 ≥4.5:1；
- 大文字与非文字 UI 对比度 ≥3:1；
- 自动化 axe 的 critical/serious 问题为 0；
- 键盘可完成导航、主题、FAQ、筛选、关系探索和项目外链；
- 焦点顺序与视觉顺序一致；
- 触控目标至少 44×44px；
- 200% 缩放无内容丢失、遮挡或双向滚动；
- 屏幕阅读器可以区分同名操作和每个来源链接。

### 11.2 已知必须修复项

- 浅色 `--color-text-tertiary` 当前用于 11–12px 文本时对比度不足，需要调整颜色或使用场景；
- 增加“跳到主要内容”链接；
- 来源页把重复“打开来源”改为包含来源名称的可访问名称；
- 关系图不能只靠颜色、位置或 hover 传达含义；
- 关闭 disclosure 的内容不进入键盘焦点顺序；
- 主题初始化脚本需要为未来 CSP 记录 hash、nonce 或外部脚本策略。

### 11.3 响应式断点验收

至少检查 390、768、1024、1440px：

- 无页面级横向滚动；
- 任务卡、专业对照、能力网格和项目卡按优先级重排；
- 移动端先显示主要任务，不先显示来源侧栏或低频上下文；
- sticky 目录在窄屏退化为普通 disclosure；
- 主题、菜单和品牌在 390px 不互相挤压；
- 卡片不通过缩小到不可读字号来保持多列。

## 12. 性能、SEO 与隐私

### 12.1 性能预算

- 移动网络 p75：LCP ≤2.5s、INP ≤200ms、CLS ≤0.1；
- 首屏媒体设置明确尺寸，禁止布局跳动；
- 首屏只预加载一个真正影响 LCP 的资源；
- 首屏外图片默认延迟加载；
- 关系图和图标不能成为阻塞脚本；
- 视觉回归中同时记录页面高度与首屏任务入口位置。

### 12.2 SEO

- 保持现有 canonical、sitemap 和 robots；
- 详情页提供页面级 title、description、canonical 和 OG 信息；
- 生产构建/发布门禁拒绝 `https://hseehub.example` 占位域名；
- 装饰图不进入结构化内容；信息图的文字等价内容可被服务端输出；
- 改版不改变现有稳定 slug，确需变更时提供重定向。

### 12.3 匿名测量

在学校/部署方确认分析工具、隐私说明、保留周期和 Cookie 要求之前，不默认接入第三方追踪。

先通过人工走查记录：

- 首次点击的入口；
- 选择入口耗时；
- 是否完成目标任务；
- 不理解的词汇；
- 选择项目所需时间；
- 中途返回、迷路或放弃位置。

若后续获批匿名分析，最小事件为：

```text
home_task_selected { task }
major_compare_opened
capability_opened { capabilityId }
project_selected { projectId, entryPoint }
resource_opened { projectId, resourceId, status }
filter_changed { filterName, activeCount, resultCount }
```

事件不得包含健康信息、自由文本、学生身份或完整 URL 查询内容。

## 13. 测试与质量门禁

### 13.1 自动化测试层

| 层级 | 工具建议 | 最低覆盖 |
| --- | --- | --- |
| Schema/关系 | Vitest | 类型、关系 ID、来源、短文案预算、媒体、资源状态、安全规则 |
| 页面投影 | Vitest | 首页模型、项目目录最小字段、反向关系、排序 |
| 组件 | Testing Library（按需） | Disclosure、可链接关系标签、筛选 chip、无结果恢复 |
| E2E | Playwright | 3 条核心任务流、移动菜单、主题、FAQ、筛选 URL、404 |
| 可访问性 | axe + 人工 | 关键页 serious/critical=0，键盘与读屏 |
| 视觉回归 | Playwright screenshot | 390/1440、亮/暗、关键页、200% 缩放 |

### 13.2 `npm run check` 目标

最终门禁至少包含：

```text
source lint
content/schema check
relationship check
link protocol check
typecheck
unit tests
production build
critical E2E smoke
axe smoke
```

真实外链探测不放入每次本地构建的阻塞链，进入定时任务和发布前检查。

### 13.3 CI

仓库 CI 至少执行：

1. `npm ci`；
2. 完整 `npm run check`；
3. 关键 E2E/axe；
4. 保存失败截图与测试报告；
5. PR 预览或等价可访问构建产物；
6. 主分支发布前检查生产域名配置；
7. 记录部署版本和回滚目标。

### 13.4 人工验收

自动化绿色不替代以下人工项：

- 5–8 名目标学生走查；
- 至少 1 名专业内容负责人复核两专业侧重与同题双解；
- 键盘完整任务流；
- NVDA/VoiceOver 等至少一种屏幕阅读器；
- 200% 缩放；
- 亮暗主题和高对比需求；
- 外链内容、许可与替代入口人工复核；
- 医学与安全措辞复核。

## 14. 实施阶段

### T0：基线与保护网

交付：

- 固定当前路由、内容数量、构建体积和关键截图基线；
- 为 3 条核心任务流建立 Playwright smoke；
- 增加基础 axe 与 390/1440 视觉基线；
- 记录当前首页文字量、页面高度和首屏入口位置；
- 明确预览、生产和回滚环境负责人；
- 确认正式托管是否支持 SSR，并按 §7.3 记录 `/projects` 渲染 ADR；无法确认时选择静态方案。

退出条件：

- 当前 `npm run check` 和新增 smoke 全绿；
- 基线数据可在 CI 或本地重复获得；
- `/projects` 的 SSR 或静态路径已经确定，目标托管能力与验收方法明确；
- 未改变现有内容事实和 URL。

### T1：内容与组件边界

交付：

- Zod 单一内容 schema；
- `server-only` 内容读取与操作型查询；
- 首页/项目/关系的最小页面投影；
- 拆分 UI、内容卡、Shell 和视觉组件；
- 消除完整 JSON 客户端依赖与未使用 props；
- 增加短文案、媒体和资源状态字段及校验。

退出条件：

- 客户端 chunk 不含完整内容 JSON；
- `/projects` 只接收最小投影；
- schema、应用读取和构建校验使用同一规则；
- 所有既有路由、canonical 和内容关系无回归；
- 首页 JS 不高于基线，`/projects` 路由 JS 达到或接近 12KB 目标。

### T2：任务化首页

交付：

- 新任务入口区；
- 双专业一屏对照；
- 8 项能力紧凑入口；
- 3 张项目结果预览；
- 场景/FAQ/来源紧凑收口；
- 四年故事和完整 FAQ 从首页移出；
- 桌面、移动、亮暗主题视觉完成。

退出条件：

- 满足 §6.2 的首页预算；
- 3 个核心任务入口首屏可见且键盘可达；
- 首页不再渲染完整双解、完整能力卡、完整四年故事和默认展开 FAQ；
- 首屏至少有 4 个有效任务链接；
- 信息视觉而非纯装饰满足模块验收。

### T3：关系闭环与关键页面

交付：

- 专业对照、能力、项目、场景和详情模板改造；
- 所有实体关系标签可导航；
- 项目筛选渐进披露；
- 外部资源状态与替代入口；
- 详情页相关内容与明确下一步。

退出条件：

- 3 条核心任务流均不超过 3 次操作；
- 各实体关系正反向抽查通过；
- 3 个项目无需筛选即可比较，更多筛选默认收起；
- 分享筛选 URL、无结果和一键恢复通过 E2E；
- 单项外链失效不阻断其他内容。

### T4：学生验证与发布收口

交付：

- 目标学生走查与问题清单；
- 教师/内容负责人复核；
- 完整 a11y、响应式、性能和外链复核；
- CI、预览、生产配置和回滚演练；
- 将发现的问题修复或记录为有负责人、有条件的后续项。

退出条件：

- §15 的 P0 全部通过；P1 全部完成测量，未达目标项有数据、负责人和后续决定；
- 生产域名不再使用占位值；
- 发布版本、回滚目标和维护者明确；
- Phase 1.5 才可标记完成，并重新评估是否有证据进入 Phase 2。

### 15.3 学生走查脚本

测试者不先阅读产品介绍，由主持人依次给出：

1. “请找出两个专业共同学习的内容，以及它们各自更强调什么。”
2. “请选择一个能力，告诉我哪些课程能支持它，以及它还能用在哪些项目或场景。”
3. “你现在有大约 1–2 小时，请选一个想尝试的项目，并告诉我需要什么、会产出什么。”

主持人只观察，不提示入口。记录首点、耗时、回退、停顿、错误理解和最后复述。

## 16. 发布、回滚与维护

### 16.1 发布策略

- 以完整 Phase 1.5 作为一个可回滚版本，不在生产环境长期保留半套新旧首页；
- PR 预览用于学生/教师走查；
- 合并前保存旧首页关键截图、构建产物标识和部署版本；
- 发布后检查首页、3 条核心任务流、主题、项目外链和 404；
- 监测到严重导航、可访问性、内容或性能回归时回滚到上一稳定版本。

### 16.2 内容维护

- 专业与课程事实按培养方案版本维护；
- 短摘要是展示投影，不得改变长文事实含义；
- 每学期至少复核一次课程解释、项目外链、资源许可和工具版本；
- 媒体资产与文字内容使用相同的来源/许可/核验机制；
- 首页精选内容必须由可解释规则决定，不使用未定义的“智能推荐”。

## 17. 风险与控制

| 风险 | 早期信号 | 控制 |
| --- | --- | --- |
| 减字变成删证据 | 卡片短了，但找不到来源/风险 | L0/L1/L2 分层；详情完整保留 |
| 视觉化变成装饰化 | 大图增加但仍不能帮助选择 | 只认可对照、关系、产物和状态视觉 |
| 首页再次膨胀 | 每个内容负责人都要求上首页 | 最多 5 模块与短文案 schema 门禁 |
| 关系图不可访问 | 只能靠鼠标/颜色理解 | 语义链接、文字等价、键盘和读屏测试 |
| 重构破坏内容正确性 | 页面更漂亮但版本/关系串错 | 单一 schema、页面投影测试、内容负责人复核 |
| 客户端包继续携带全量内容 | 纯 UI 组件导入内容模块 | `server-only`、模块边界和 bundle 检查 |
| 过早进入平台功能 | 又开始做账号/社区/CMS | 非目标冻结，Phase 1.5 退出后再用证据评估 |
| 图片拖慢首屏 | LCP、CLS 恶化 | 固定尺寸、现代格式、单一 LCP 资源、预算门禁 |
| 3 个项目却保留复杂筛选 | 用户先操作表单才看内容 | 结果优先，更多筛选收起，>6 项再评估 |
| 外链探测拖垮构建 | 网络波动导致 PR 全红 | 构建只验 schema；真实探测定时/发布前运行 |
| CSS 一次性重写引发回归 | 大量无关页面同时变化 | 保留全局基线，按组件迁移 CSS Modules |

## 18. 开工清单与文件影响

建议按以下顺序创建实施任务：

1. 测试与 CI 基线：`package.json`、测试配置、`.github/workflows/*`（或等价 CI）。
2. 内容内核：把 `lib/content.ts` 迁移为 `lib/content/*`，让校验脚本复用 schema。
3. 客户端边界：拆分 `components/site.tsx`，让 `project-browser.tsx` 只依赖内容无关 UI 与最小投影。
4. 内容字段：为 `content/site-data.json` 增加短摘要、任务标签、媒体和资源状态。
5. 首页：重写 `app/page.tsx` 与对应组件/样式，删除旧首页重复渲染。
6. 关系闭环：修改专业课程、能力、项目、场景索引和详情页。
7. 项目发现：简化 `components/project-browser.tsx`，保留 URL 状态与无结果恢复。
8. 可访问性：SkipLink、对比度、链接名称、关系图语义、200% 缩放。
9. 媒体资产：新增 `public/` 下的本地视觉并通过资产 schema 校验。
10. 发布收口：真实外链状态、预览、生产域名、性能和回滚演练。

## 20. Phase 1.5 完成定义

只有同时满足以下条件，本阶段才算完成：

1. 任务化首页、关键索引和详情关系已按本 Spec 上线；
2. P0 验收全部通过，P1 未通过项有明确数据、负责人和后续决策；
3. 目标学生和内容负责人已实际走查，而非只由开发者自验；
4. 完整内容不进入客户端，schema、投影和组件边界可测试；
5. 可访问性、性能、外链状态、CI、预览、生产域名和回滚有证据；
6. 没有以体验改版为由扩大到登录、社区、数据库或敏感数据处理；
7. 团队基于真实走查或行为证据重新评估 Phase 2，而不是按旧路线自动进入。
